why it exists

Every team needs the same warehouse to run, reproducibly

Give the warehouse-systems estate a reproducible runtime on an existing k3s cluster (kube context k3s-multipass, ADR 0011): scripts/up.sh applies three Terraform layers — cluster, platform (Postgres + PgBouncer, Kafka, Istio, ArgoCD, observability, Kong and an Nginx web gateway) and one state per application…

Today

Three Terraform layers, a shared Postgres, Kafka, two gateways and an observability plane host the fleet; ArgoCD installs each chart.

The catch

Postgres, PgBouncer and Kafka are single points of failure, alerts reach nobody, and hand-kept lists drift behind the registry.

Give the warehouse-systems estate a reproducible runtime on an existing k3s cluster (kube context k3s-multipass, ADR 0011): scripts/up.sh applies three Terraform layers — cluster, platform (Postgres + PgBouncer, Kafka, Istio, ArgoCD, observability, Kong and an Nginx web gateway) and one state per application — and ArgoCD installs each service's own chart from its repo's develop. kind is banned and nothing is built locally: every image is built on GitHub (publish-images) and pinned in terraform/targets/k3s.images.yaml. It owns the environment, not the workloads: a context is registered by one entry in terraform/apps.yaml plus its helm-values files. It also owns fleet-level published facts (the process-path catalogue) that no single bounded context should own.
what it does

One script delivers the cluster, data, events and dashboards

One-script platform

One script applies the cluster, platform and per-application Terraform layers.

One application registry

Each entry in apps.yaml is one module instance and one ArgoCD application.

Images from GitHub only

Arm64 images are built on GitHub and pinned; apply never builds locally.

Two separate gateways

Kong serves APIs, Nginx serves screens, and a test keeps the two apart.

Shared data plane

One Postgres with a database and role per application, pooled, plus one Kafka broker.

Observability plane

One collector feeds Jaeger, Prometheus and Loki into Grafana, with 46 dashboards.

competitive position

Against the market leaders, we cover part of the ground

PartialPlatform, Observability & Delivery vs Blue Yonder, Manhattan (zero-downtime CD, multi-AZ failover), SSI Schäfer (KPI telemetry)

Where we match or lead

  • Open, correlated telemetry: OTel Collector, Jaeger, Prometheus, Grafana, Loki + Alloy, Kiali, Kong metrics
  • Metric exemplars link to traces; log lines link to traces (two-way navigation)
  • Generated per-context Grafana dashboards: edge RED, business counters, Go runtime, logs
  • Harness engineering: mutation gates, architecture fitness tests, black-box e2e and soak

Gaps to close

  • High No alerting: Alertmanager disabled; no SLOs or error budgets
  • High Telemetry is ephemeral: Jaeger in-memory, Prometheus 24 h emptyDir, Loki no persistence
  • High Local kind cluster: no HA, multi-AZ failover or zero-downtime rollout evidence
  • Medium /healthz does not check the database

Leader capabilities are vendor-published; gaps reflect repo docs reviewed in November 2026.

what could go wrong · and what we do about it

Our biggest risk is one exposure mistake publishing open data

Auth is off by decision; edges must stay loopback-only

Every REST and MCP endpoint and ArgoCD are unauthenticated BY DECISION (auth reverted 2026-09-11)…

→

Both edges stay loopback-bound and the exposure-policy test keeps them separate.

Postgres, PgBouncer and Kafka are single points

Single Postgres, single PgBouncer replica and a single Kafka broker are deliberate single points of failure…

→

Deliberate single points; PgBouncer replicas and a disruption budget are noted if needed.

Deploys depend on GitHub image builds and pins

Deploys depend on GitHub: an image reaches the cluster only after publish-images ran on the merged develop and the pin is committed…

→

No mitigation on the roadmap yet: this one needs an owner.

Databases outlive removed apps; manual cleanup needed

Roles and databases come from Jobs and survive removal of an application: dropping a database is a manual step needing the owner's OK…

→

Every REST and MCP endpoint and ArgoCD are unauthenticated BY DECISION (auth reverted 2026-09-11); both product edges must stay loopback-only (port-forwards to 127.0.0.1, CORS load-bearing), and k3s's bundled Traefik is forced to ClusterIP for the same reason Single Postgres, single PgBouncer replica and a single Kafka broker are deliberate single points of failure; the PgBouncer wildcard pool of 12 per database times 40 OLTP databases (480) can exceed max_connections=250 under simultaneous saturation (pgbouncer.tf still budgets 14 databases) Deploys depend on GitHub: an image reaches the cluster only after publish-images ran on the merged develop and the pin is committed; apply does not pick up chart changes, ArgoCD reads develop Roles and databases come from Jobs and survive removal of an application: dropping a database is a manual step needing the owner's OK; never terraform destroy the cluster (leaves ~60 phantom resources in state) Hand-kept lists drift: the Makefile CHARTS list lacks 2 of 45 registry entries, and INCIDENTS.md records warehouse-planning being missed from every fleet list Alertmanager has a null receiver: the 31 alert rules fire but nothing is delivered anywhere
